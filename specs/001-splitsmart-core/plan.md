# Implementation Plan: SplitSmart Core

**Branch**: `001-splitsmart-core` | **Date**: 2026-11-03 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-splitsmart-core/spec.md`

## Summary

SplitSmart will be delivered as a desktop MVP that preserves the full customer requirements
inventory while implementing the prioritized Java Swing subset. A layered desktop architecture
with MVC presentation boundaries will separate Swing views and controllers from application
services, domain rules, and persistence.

## Technical Context

**Language/Version**: Java 21

**Primary Dependencies**: Java Swing, Maven, JUnit 5, PlantUML

**Storage**: Repository abstraction with a desktop-local implementation; persistence technology
is deferred to Phase 0 research.

**Testing**: Maven Surefire, JUnit 5 unit and integration tests

**Target Platform**: Desktop Java 21 with Java Swing; the customer primary platform remains
web-based and is outside this MVP implementation.

**Project Type**: Desktop application

**Performance Goals**: Responsive normal actions and reports for the desktop MVP's expected
small-group data set; no customer performance target is specified.

**Constraints**: Java 21, Maven, Swing, exact decimal arithmetic, GUI/business separation,
human review, and traceable requirement IDs.

**Scale/Scope**: Accounts, groups, expense review, balances, payments, notifications, summaries,
and defined reports for the desktop MVP.

## Architecture Decision

### Options Compared

| Architecture | Complexity | Maintainability | Testability | Extensibility | Implementation effort | Suitability |
|---|---|---|---|---|---:|---|
| Tightly coupled desktop application | Low initially | Low | Low | Low | Low | Poor: Swing widgets entangle rules and storage |
| Layered architecture | Moderate | High | High | High | Moderate | Strong: isolates rules, services, persistence, and UI |
| MVC desktop architecture | Moderate to high | High if strict | High | High | Moderate | Strong: clear UI roles, but MVC alone can leave business logic scattered |

### Recommendation

Adopt a layered architecture with MVC boundaries in the presentation layer. Domain entities and
value objects contain invariant-enforcing behavior. Application services coordinate users,
groups, expenses, approvals, payments, notifications, and reports. Swing views handle widgets and
rendering; Swing controllers or presenters translate user intent and application results into view
updates. Infrastructure repositories isolate persistence and local file receipt storage.

This decision provides the separation required by the constitution while avoiding a frame-level
network of coupled Swing listeners. It is more maintainable and testable than a tightly coupled
desktop application and more complete for SplitSmart than MVC alone, because MVC does not by
itself prevent domain and persistence dependencies from entering controllers or views.

### Architectural Decisions

1. The domain and application layers depend inward only; Swing and infrastructure depend on them.
2. Application services are the business transaction boundary and expose no Swing types.
3. Repository interfaces are owned by the domain/application boundary and implemented by
   infrastructure adapters.
4. Monetary calculations use exact decimal values, cent precision, half-up rounding, and payer
   remainder assignment.
5. The presentation layer follows MVC/presenter conventions, with views not performing financial
   calculations or persistence.
6. Desktop-local notifications are generated by the application; delivery policy is retained as a
   requirement for finalization.
7. Implementation structure and class names are intentionally deferred to detailed design.
